# ctr-swerve-test (Phoenix 6 / Tuner X reference project)

A faithful reference copy of what the **CTRE Phoenix Tuner X Swerve Project Generator** produces, adapted for our hardware on **SDS MK5n** modules. Use it to learn the layout and to start writing subsystems and autos before the motors arrive. When the real motors are on the bus, run the actual generator and let it overwrite `TunerConstants.java`.

Driver controls are documented in [CONTROLS.md](CONTROLS.md).

## Our hardware to Phoenix mapping

| Robot part | Our device | Phoenix class | Where it appears |
|---|---|---|---|
| Module | SDS MK5n | (geometry) | gear ratios + wheel radius in `TunerConstants` |
| Drive motors (x4) | Kraken X60 | `TalonFX` | `kDriveMotorType = TalonFX_Integrated` |
| Steering motors (x4) | Kraken X44 | `TalonFX` | `kSteerMotorType = TalonFX_Integrated` |
| Azimuth encoders (x4) | CANcoder | `CANcoder` | `kSteerFeedbackType = FusedCANcoder` |
| Heading sensor | Pigeon 2.0 | `Pigeon2` | `kPigeonId` |

Note: both the Kraken X60 and the Kraken X44 are just a motor with an integrated TalonFX controller, so in code they are identical device types (`TalonFX`). The only differences that matter are the gains (kV/kA) and current limits, which get tuned per motor.

The Tuner X "SDS MK5n" module preset fills these in for you once you pick R2 in the dropdown.

## File map

```
src/main/java/frc/robot/
  Main.java                       Entry point. Do not edit.
  Robot.java                      TimedRobot. Runs the CommandScheduler each loop.
  RobotContainer.java             Joystick bindings + default drive command. This is where YOU work.
  Telemetry.java                  Publishes pose/module state to NetworkTables + hoot log. Generated.
  generated/
    TunerConstants.java           THE generated file. IDs, gear ratios, gains, offsets. Regenerated by Tuner X.
  subsystems/
    CommandSwerveDrivetrain.java  Wraps CTRE's SwerveDrivetrain as a command-based Subsystem. Generated.
```

## The three files that matter, in order

### 1. `generated/TunerConstants.java`  (the heart)
This is the only file Tuner X overwrites. It holds:
- **CAN IDs** for every drive motor, steer motor, and CANcoder, plus the Pigeon ID.
- **Module geometry**: X/Y position of each wheel relative to robot center (drives the kinematics).
- **Gear ratios and wheel radius**: these come from your swerve MODULE (MK4i, MK4n, WCP X, etc.), not the motors. Tuner has a dropdown that fills these in.
- **Gains** (`steerGains`, `driveGains`): PID + feedforward. Placeholders until you run SysId.
- **Encoder offsets**: the magic numbers that tell each wheel where "straight ahead" is. Tuner measures these while you physically point the wheels forward.
- `createDrivetrain()`: the one factory call `RobotContainer` uses to build the whole drivetrain.

Module construction order is **Front Left, Front Right, Back Left, Back Right**. If you ever need one module directly, `getModule(2)` is Back Left.

### 2. `subsystems/CommandSwerveDrivetrain.java`
CTRE's `SwerveDrivetrain` does all the odometry and module control. This subclass adds:
- `implements Subsystem` so it plugs into WPILib command-based.
- `applyRequest(...)`: the main way you command the drive. You hand it a `SwerveRequest` (FieldCentric, RobotCentric, Brake, PointWheelsAt, etc.).
- **SysId routines**: pre-wired characterization tests for drive, steer, and rotation. Hold the button combos in `RobotContainer` to run them, then feed the `.hoot` log into SysId to get your gains.
- **PathPlanner AutoBuilder** setup in `configureAutoBuilder()`.
- **Operator perspective** handling in `periodic()`: automatically flips "forward" depending on Blue vs Red alliance.
- A simulation thread so you can drive it on a laptop with no robot attached.

You usually do not edit this file. You call it from `RobotContainer`.

### 3. `RobotContainer.java`  (where you actually work)
Sets the default command: left stick translates, right stick rotates, field-centric, with a 10% deadband. Button map on an Xbox controller:
- **A**: X-lock the wheels (brake).
- **B**: point all wheels where the left stick aims.
- **D-pad up/down**: creep straight forward/back (robot-centric).
- **Left bumper**: reset field-centric heading (zero the gyro to current facing).
- **Back/Start + X/Y**: run the four SysId characterization sweeps.
- **Auto chooser** is published to SmartDashboard via PathPlanner.

`MaxSpeed` here is your *desired* teleop cap. `kSpeedAt12Volts` in TunerConstants is the *measured physical* top speed. Keep those distinct.

## What to do before the motors arrive

You can do a lot without hardware:
1. Install WPILib 2026 (VS Code) and open this folder as an FRC Java project.
2. Add the vendordeps: **Phoenix 6** (CTRE) and **PathPlannerLib**. In VS Code: WPILib icon > "Manage Vendor Libraries" > "Install new (online)" and paste CTRE's and PathPlanner's JSON URLs.
3. Build it. Then run **Simulate Robot Code** and drive the sim with a controller or keyboard, and watch the module states in the sim GUI / AdvantageScope.

## What changes once the motors are here

1. In Tuner X, give each device a CAN ID and label (Pigeon, 4 CANcoders, 4 drive Krakens, 4 steer Krakens). Confirm all are on the same CAN bus.
2. Run **Mechanisms > Swerve Project Generator**. Pick your module type, enter IDs, and follow the wizard (it has you spin wheels to set inverts and measure encoder offsets).
3. Choose "Generate only TunerConstants" and let it overwrite `src/main/java/frc/robot/generated/TunerConstants.java`. Everything marked `TODO(2026)` in that file becomes real.
4. Run the SysId routines (button combos above) to replace the placeholder `driveGains` / `steerGains`.
5. Verify `kSpeedAt12Volts` by driving full-out and reading the reported speed, then set the module X/Y positions to your real wheelbase.
